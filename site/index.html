Make a Linux server quiet enough for microseconds.

A field guide, with working scripts, for turning a RHEL 8, 9 or 10 host into a deterministic, low-jitter machine. Every guide explains what the kernel does, why each value was chosen, how to verify it, and how to undo it.

Read this first. These settings are for dedicated hosts that run a few well-understood, latency-critical processes. They trade power, throughput, flexibility and, in places, security for predictable latency. Some options are opt-in and marked, and need written approval. Read the warnings and the cases where you should not apply any of this.

How it works

One config file describes your hardware. The scripts read it, and every step shows what it would do before it does it.

Measure

Capture a baseline: percentiles and a host bundle, before any change.

Design

Decide which CPUs are critical, which run the OS, and where the NIC sits.

Apply

--dry-run first, then apply once and reboot once. Every file is backed up.

Verify, then measure

A PASS, WARN or FAIL report proves the configuration. Your histograms prove the benefit.

Use cases: from symptom to result

Fifteen stories. Each one has the diagnosis commands, the exact configuration lines, the result and the rollback. The numbers are illustrative and labeled, never presented as benchmarks.

1. The quiet core

A clean median and a comb of spikes: stop the tick on the CPU that spins.

2. Critical and non-critical, side by side

Give every thread a home: one critical thread per isolated CPU, everything else on the OS CPUs.

3. The noisy neighbor

An agent bursts onto a critical core: fence it with a cpuset and a budget.

4. One NIC, one queue, one CPU

Move the interrupt off the spinning thread, and give one flow its own queue.

5. Page faults on the hot path

Reserve huge pages per node and pre-touch the heap: the faults move to start-up.

6. Two sockets, one mistake

A histogram with two humps: the thread, its memory and the NIC belong on one node.

7. The freeze nobody logs

A rare spike with a clean OS log: count SMIs and fix the firmware.

8. Capstone: stock to tuned in one afternoon

The whole path with an honest before and after. The ladder shown is illustrative.

9. The two-millisecond burst

A low average load and a few thousand lost packets per batch. Size the ring and the socket buffer to the burst.

10. Line rate without the kernel

Packets lost all the time, with the rings at the maximum. Count the nanoseconds per packet, then queues, then bypass.

11. The first message after a quiet spell

Fast under load, slow after a lull: the idle CPU fell into C6. Keep it out of deep idle states.

12. The sibling that shares your core

Slow only while another thread is busy: the two CPUs are halves of one core. Turn Hyper-Threading off, or one thread per core.

13. Turbo, the lottery

Same hosts, different medians: the clock follows heat and power limits. Decide turbo by measuring it on and off.

14. The spinner that stalled the kernel

FIFO 99 "so it always wins": a 50 ms stall every second, then starved kernel threads. Spin as SCHED_OTHER.

15. The coalescing timer

Slower at light load than in bursts: a NIC nobody listed kept the driver's coalescing. Adaptive off, rx-usecs 0.

See where a burst is lost

A ring, a socket buffer, a drain and a reader are four numbers, and the loss depends on all of them. The simulator takes a burst and your sizes, shows where the packets are dropped and which counter reports it, and says how big each queue must be to lose nothing. The figures are illustrative.

Quick start

sudo mkdir -p /etc/lowlat && sudo cp scripts/lowlat.conf.example /etc/lowlat/lowlat.conf
sudo vi /etc/lowlat/lowlat.conf              # describe your CPUs, NICs and memory

scripts/apply-all --plan                     # what applies on this host class
scripts/apply-all --dry-run | less           # every command and file, nothing changed
sudo scripts/apply-all --apply               # apply the guides + install lowlat-runtime.service
sudo systemctl reboot
scripts/verify-tuning                        # PASS/WARN/FAIL for every guide

Bare metal gets the full treatment. A virtual machine gets the subset that helps without pretending to isolate what the hypervisor controls. Choose your scenario.
